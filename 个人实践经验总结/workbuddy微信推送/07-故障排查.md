# 07 · 故障排查手册

> 按错误现象查。先看脚本终端输出，再看自动化日志，最后才查数据库。

---

## 1. 一分钟诊断流程

```text
脚本能否找到配置？
  ├─ 否 → 检查 settings.json 与 ClawBot 绑定
  └─ 是
      ↓
HTTP 请求是否成功返回 JSON？
  ├─ 否 → 检查网络、证书、代理、域名
  └─ 是
      ↓
返回 ret=-2？
  ├─ 是 → 微信给 ClawBot 发一条消息，再试
  └─ 否
      ↓
返回 errcode=-14？
  ├─ 是 → 检查 POST、完整 botToken 和 5 个协议头
  └─ 否 → 保存完整响应（脱敏后）继续定位
```

## 2. `ret=-2: prepare failed`

### 现象

```text
RuntimeError: 发送失败 ret=-2: prepare failed
```

### 含义

微信服务端拒绝准备主动消息。当前已验证的主要原因是：**用户与 bot 的主动推送会话已失效**。

### 解决

1. 用户打开微信中的 ClawBot 会话
2. 主动发一条任意文本，如“1”
3. 等待 bot 收到或回复
4. 重新运行脚本

通常立即恢复。

### 不要做

- 不要连续重试几十次
- 不要重新安装 Python
- 不要修改 `channel_version`
- 不要删除 `settings.json` 或 cursor 文件
- 不要因为看到 -2 就重新扫码绑定

### 为什么重试没用

这是服务端会话状态，不是网络抖动。客户端发送相同请求不会自动刷新会话，必须由用户主动发消息建立新的上下文。

## 3. `errcode=-14: session timeout`

### 现象

```json
{"errcode":-14,"errmsg":"session timeout"}
```

### 先别相信错误文案

实测中这个错误经常是**请求构造错误**，不是真正的微信聊天会话过期。

### 按顺序检查

#### 3.1 请求方法是不是 POST

错误：

```http
GET /ilink/bot/getupdates
```

正确：

```http
POST /ilink/bot/getupdates
POST /ilink/bot/sendmessage
```

#### 3.2 botToken 是否完整

正确：

```text
d2cc68bff868@im.bot:0600002xxxxxxxxxxxxxxxx
```

错误：

```text
0600002xxxxxxxxxxxxxxxx
```

token 必须包含 `accountId:` 前缀。

#### 3.3 请求头是否完整

必须全部存在：

```text
Content-Type: application/json
AuthorizationType: ilink_bot_token
Authorization: Bearer <完整botToken>
X-WECHAT-UIN: <随机uint32十进制字符串的base64>
iLink-App-Id: bot
iLink-App-ClientVersion: 132102
```

#### 3.4 协议版本是否正确

```json
{"channel_version":"2.4.6","bot_agent":"OpenClaw"}
```

不要写 `workbuddy-desktop-1.0.0` 或其他自造版本。

#### 3.5 以上都对仍报 -14

此时才考虑凭据已被服务端撤销：

1. 在 WorkBuddy 中解绑微信 ClawBot
2. 重新扫码绑定
3. 确认 `settings.json` 中 token 已更新
4. 微信主动发一条消息后重试

## 4. `未找到启用的 weixinClawBot 通道配置`

### 原因

脚本在下面的路径中没找到启用节点：

```text
claw.users.*.channels.weixinClawBot.enabled == true
```

### 排查

```bash
"C:/Users/<用户名>/.workbuddy/binaries/python/versions/3.13.12/python.exe" -c "
import json,os
p=os.path.expanduser('~/.workbuddy/settings.json')
s=json.load(open(p,encoding='utf-8-sig'))
print(json.dumps(s.get('claw',{}),ensure_ascii=False,indent=2)[:5000])
"
```

确认：

- 文件路径正确
- `claw` 节点存在
- 至少有一个 `weixinClawBot`
- `enabled` 是布尔值 `true`，不是字符串 `"true"`

没有节点就回 WorkBuddy 重新绑定。

## 5. `FileNotFoundError: settings.json`

### 原因

- 当前 Windows 用户与绑定 WorkBuddy 的用户不是同一个
- 在服务账号、容器或 WSL 中运行，`~` 指向了别的 home

### 解决

确认脚本运行时的 home：

```bash
python -c "import os; print(os.path.expanduser('~'))"
```

如果跨用户运行，建议改脚本支持环境变量：

```python
path = os.environ.get(
    "WORKBUDDY_SETTINGS",
    os.path.expanduser("~/.workbuddy/settings.json")
)
```

然后：

```bash
WORKBUDDY_SETTINGS="C:/Users/张三/.workbuddy/settings.json" python send_wechat.py "测试"
```

## 6. HTTP / 网络错误

### `URLError: [SSL: CERTIFICATE_VERIFY_FAILED]`

系统证书链或代理拦截。不要通过关闭 SSL 校验解决。应：

- 检查企业代理证书是否正确安装
- 尝试系统网络而非抓包代理
- 用浏览器访问 `https://ilinkai.weixin.qq.com` 验证域名可达（返回非网页内容也正常）

### `TimeoutError` / `timed out`

- 网络临时波动
- 域名被代理或防火墙拦截
- 服务端短暂不可用

这类错误可以重试 1–2 次。与 `ret=-2` 不同，网络异常才值得重试。

### HTTP 401 / 403

优先检查 token 和请求头。也可能是 token 被解绑后失效。

## 7. 终端显示成功，但微信没收到

### 检查 1：发错用户

`to_user_id` 来自 `settings.json` 的 `userId`。如果历史上绑定过多个微信账号，脚本会取**第一个 enabled 的通道**。

改进方案：

- 只保留一个通道 `enabled=true`
- 或给脚本增加 `--account-id` 参数，精确选择通道

### 检查 2：客户端去重

如果复用了同一个 `client_id`，服务端可能将后续请求视为重复而不再次投递。正常脚本每次都会生成新 ID。

### 检查 3：微信侧免打扰或折叠

消息可能已进入会话但未弹通知。打开 ClawBot 会话确认，不要只看系统通知。

### 检查 4：message_id 是否真实

成功响应应包含 `message_id`。若输出 `N/A`，保存响应 body 继续分析。

## 8. 自动化任务不执行 Bash

### 日志出现

```text
[tool-permission] ASK tool=Bash ... Approval required for Bash
```

先继续看后面的日志：

```text
Auto-approving tool Bash for session (FullAccess mode)
```

有这一行说明权限已自动通过，**不是失败根因**。

若确实停在审批：

- 检查自动化的 `permission_mode`
- 无人值守任务要允许执行 Bash
- 确保提示词中的命令路径是绝对路径

## 9. 自动化显示成功，但微信没消息

WorkBuddy 任务本身“成功”只代表 Agent 跑完，不代表消息投递成功。

### 查原生投递表

```python
import sqlite3

conn = sqlite3.connect(
    "file:C:/Users/<用户名>/.workbuddy/workbuddy.db?mode=ro",
    uri=True,
)
rows = conn.execute("""
SELECT automation_name, status, attempt_count, max_attempts,
       last_error_code, last_error_message, created_at
FROM automation_delivery_outbox
ORDER BY created_at DESC LIMIT 30
""").fetchall()
for row in rows:
    print(row)
```

重点看：

- `status`
- `last_error_code`
- `last_error_message`
- `attempt_count / max_attempts`

如果这里是 `ret=-2: prepare failed`，说明真正失败发生在投递阶段。

## 10. 多个 bot 账号导致串号

历史绑定可能残留多个 cursor 文件，例如：

```text
~/.workbuddy/claw-state/weixin/
├── 5fa47adc818f_im.bot.cursor.json
└── d2cc68bff868_im.bot.cursor.json
```

**cursor 文件多不等于配置串号。** 发送脚本实际以 `settings.json` 中第一个 `enabled=true` 的通道为准。

不要凭 cursor 文件数量就删除文件。先核对：

- `accountId`
- `botToken` 前缀
- `userId`
- `enabled`

## 11. 中文乱码

脚本已使用：

```python
json.dumps(payload, ensure_ascii=False).encode("utf-8")
```

若终端显示乱码但微信正常，是 Windows 终端编码问题，不影响请求。

如果微信内容也乱码，检查调用方是否在传参前错误编码。不要手动 `encode('gbk')`。

## 12. 安全排障清单

分享日志时必须脱敏：

| 内容 | 如何脱敏 |
|---|---|
| botToken | 只保留前 6、后 4 位，中间替换 `***` |
| userId | 中间替换 `***` |
| accountId | 可保留前 4 位，其余脱敏 |
| cursor / context_token | 全部隐藏 |
| message_id | 通常可保留，但公开资料建议替换为示例 |

绝对不要把完整 `settings.json` 上传给别人。

## 13. 已验证的真实排障案例

### 案例 A：误判“会话超时”

- 现象：`errcode=-14 session timeout`
- 第一判断：微信会话过期，需要重新扫码
- 真正原因：用 GET 调了必须 POST 的接口，且缺少协议头
- 修复：改 POST + 补齐请求头 + 使用完整 token

**教训**：错误文案不可信，先核对协议格式。

### 案例 B：误判“Bash 权限被拦截”

- 现象：日志有 `Approval required for Bash`
- 第一判断：无人值守任务没人审批
- 真正原因：后续日志显示已 auto-approve；数据库投递记录才显示 `ret=-2`
- 修复：用户给 bot 发消息刷新会话

**教训**：不要只看一行日志，要看后续状态和 outbox 真正错误。

### 案例 C：误判“会话大约一天失效”

- 成功：22:36、23:31、00:27
- 首次失败：01:22
- 结论：只隔数小时，不是一天

**教训**：没有官方公开 TTL，不要把单次实测包装成固定规律。
