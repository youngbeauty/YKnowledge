# 03 · 协议参考

> 面向二次开发。用其他语言（Node / Go / Java）重写时对照本文档即可。

---

## 1. 基础信息

| 项 | 值 |
|---|---|
| Base URL | `https://ilinkai.weixin.qq.com` |
| 协议基线 | `@tencent-weixin/openclaw-weixin@2.4.6` |
| 传输 | HTTPS + JSON |
| 方法 | **全部 POST**（二维码相关端点除外） |
| 编码 | UTF-8 |

⚠️ 用 GET 调 `sendmessage` / `getupdates` 会返回误导性的 `errcode=-14 session timeout`。

---

## 2. 请求头（所有 POST 端点通用）

```http
POST /ilink/bot/sendmessage HTTP/1.1
Host: ilinkai.weixin.qq.com
Content-Type: application/json
Authorization: Bearer {botToken}
AuthorizationType: ilink_bot_token
X-WECHAT-UIN: {uin}
iLink-App-Id: bot
iLink-App-ClientVersion: 132102
```

### 逐项说明

#### `Authorization`

```
Bearer d2cc68bff868@im.bot:0600002xxxxxxxxxxxxxxxx
       └────── accountId ──────┘└──── secret ────┘
```

⭐ **必须是完整 token，含 `accountId:` 前缀。** 这是最高频的错误来源。

只传冒号后半段 → `errcode=-14`。

#### `AuthorizationType`

固定 `ilink_bot_token`。声明这是 bot token 而非用户 token。缺失 → 401 / -14。

#### `X-WECHAT-UIN`

一次性设备标识。生成算法：

```
1. 取 4 字节随机数
2. 按小端序解释为 uint32
3. 转成十进制字符串
4. 对该字符串做 base64
```

Python：

```python
import os, base64
n = int.from_bytes(os.urandom(4), "little")
uin = base64.b64encode(str(n).encode("ascii")).decode("ascii")
```

Node：

```javascript
const crypto = require('crypto');
const n = crypto.randomBytes(4).readUInt32LE(0);
const uin = Buffer.from(String(n), 'ascii').toString('base64');
```

Go：

```go
b := make([]byte, 4)
rand.Read(b)
n := binary.LittleEndian.Uint32(b)
uin := base64.StdEncoding.EncodeToString([]byte(strconv.FormatUint(uint64(n), 10)))
```

每次请求生成新值即可，服务端不做关联校验。

#### `iLink-App-Id`

固定 `bot`。

#### `iLink-App-ClientVersion`

固定 `132102`。这是客户端版本指纹，对应 SDK 2.4.6。**不要自己编数字**，会被拒。

## 3. `POST /ilink/bot/sendmessage`

### 请求体

```json
{
  "msg": {
    "from_user_id": "",
    "to_user_id": "o9cq80-EXAMPLE_USER_ID@im.wechat",
    "client_id": "a3f9c2e1b8d74506",
    "message_type": 2,
    "message_state": 2,
    "item_list": [
      {
        "type": 1,
        "text_item": { "text": "消息内容" }
      }
    ],
    "context_token": ""
  },
  "base_info": {
    "channel_version": "2.4.6",
    "bot_agent": "OpenClaw"
  }
}
```

### 字段表

#### `msg`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `from_user_id` | string | ✅ | 固定空串 `""`，服务端从 token 推断 |
| `to_user_id` | string | ✅ | 接收方，取 `settings.json` 的 `userId` |
| `client_id` | string | ✅ | 16 位随机 hex，幂等去重键 |
| `message_type` | int | ✅ | `2` = 主动下发 |
| `message_state` | int | ✅ | `2` = 已完成（非流式） |
| `item_list` | array | ✅ | 消息内容项，至少 1 个 |
| `context_token` | string | ✅ | 会话上下文；文本可空串，媒体必填 |

#### `item_list[]`

| 字段 | 类型 | 说明 |
|---|---|---|
| `type` | int | `1` = 纯文本 |
| `text_item.text` | string | 文本内容 |

多个 item 会拼成一条消息。

#### `base_info`

| 字段 | 类型 | 说明 |
|---|---|---|
| `channel_version` | string | `"2.4.6"`，必须与 SDK 对齐 |
| `bot_agent` | string | `"OpenClaw"` |

### 成功响应

```json
{
  "message_id": 7491156072188354056
}
```

无 `ret` / `errcode` 字段，或其值为 `0`，即为成功。

### 失败响应

```json
{ "ret": -2, "errmsg": "prepare failed" }
```

```json
{ "errcode": -14, "errmsg": "session timeout" }
```

⚠️ **HTTP 状态码可能是 200**，必须解析 body 判断。

## 4. `POST /ilink/bot/getupdates`

长轮询拉消息。WorkBuddy 桌面端在用，自建方案一般不需要。

### 请求体

```json
{
  "get_updates_buf": "<上次返回的游标>",
  "base_info": {
    "channel_version": "2.4.6",
    "bot_agent": "OpenClaw"
  }
}
```

首次调用 `get_updates_buf` 传空串。返回中带新游标，需持久化。

WorkBuddy 把游标存在：

```
~/.workbuddy/claw-state/weixin/<accountId 去掉@点>_im.bot.cursor.json
```

内容形如：

```json
{"get_updates_buf":"ChAICBCqyK3X/TMYtf38q/0zEjpkMmNj..."}
```

⭐ **发送图片/文件时的 `context_token` 就从这个字段取**（原样传，不要解码）。

## 5. `POST /ilink/bot/getuploadurl`

媒体消息上传前置步骤。本方案未封装，此处仅记录端点存在。

流程大致为：`getuploadurl` → 拿到临时上传地址 → PUT 文件 → 用返回的资源 id 构造 `item_list` → `sendmessage`（此时 `context_token` 必填）。

## 7. 错误码全表

| 码 | 字段 | 含义 | 真实原因 | 处理 |
|---|---|---|---|---|
| `-2` | `ret` | `prepare failed` | 主动推送会话失效 | 让用户在微信给 bot 发条消息 |
| `-14` | `errcode` | `session timeout` | **多为请求格式错误**：token 缺前缀 / 缺请求头 / 用了 GET | 检查请求构造，**不要**误判为会话过期 |
| `0` 或缺失 | — | 成功 | — | 读 `message_id` |

### 关于 `-14` 的重要提醒

这个错误的文案是 `session timeout`，但实测中**绝大多数情况不是会话问题，而是请求格式问题**。

排查顺序：

1. 是不是用了 GET？→ 改 POST
2. `Authorization` 里 token 有没有 `accountId:` 前缀？
3. `AuthorizationType` 头有没有带？
4. `X-WECHAT-UIN` 有没有带？
5. `iLink-App-Id` / `iLink-App-ClientVersion` 有没有带？
6. `channel_version` 是不是 `2.4.6`？

以上全对还报 -14，才考虑凭据本身失效（重新绑定）。

## 9. 其他语言实现要点

无论用什么语言，只要保证：

1. POST + JSON
2. 六个请求头齐全，token 带前缀
3. `channel_version = "2.4.6"`
4. `X-WECHAT-UIN` 按算法生成
5. 解析 body 判断 `ret` / `errcode`，不能只看 HTTP 200

就能跑通。整套协议没有签名、没有加密、没有时间戳校验，非常直白。
