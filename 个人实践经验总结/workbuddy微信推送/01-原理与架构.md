# 01 · 原理与架构

---

## 1. ClawBot 是什么

微信里那个能跟 WorkBuddy 对话的机器人，**不是**微信公众号，**不是**微信客服，**不是**企业微信应用。

它是微信 **iLink Bot**（内部代号 `im.bot`）体系下的一个机器人账号：

| 特征 | 说明 |
|---|---|
| 服务域名 | `https://ilinkai.weixin.qq.com` |
| 账号格式 | `d2cc68bff868@im.bot`（12 位 hex + `@im.bot`） |
| 用户标识 | `o9cq80-EXAMPLE_USER_ID@im.wechat`（openid 风格 + `@im.wechat`） |
| 绑定方式 | 扫码（`bot_type=3`） |
| 官方 SDK | `@tencent-weixin/openclaw-weixin` |

它和公众号最大的区别：**没有"48 小时内可回复"这种明文规则，但有自己的一套会话时效机制**（详见第 5 节和 `08-已知限制.md`）。

## 2. 完整链路

```
┌─────────────┐                    ┌──────────────────────┐
│   你的微信   │ ◄────────────────► │  ilinkai.weixin.qq.com│
└─────────────┘                    └──────────────────────┘
                                            ▲   ▲
                          ┌─────────────────┘   └──────────────┐
                          │ 收(getupdates)          发(sendmessage)
                          │ 长轮询                    HTTP POST
                          │                                    │
                  ┌───────┴────────┐                  ┌────────┴─────────┐
                  │ WorkBuddy 桌面端 │                  │  send_wechat.py  │
                  │  (常驻轮询进程)   │                  │  (任意时刻调用)   │
                  └────────┬───────┘                  └────────┬─────────┘
                           │                                    │
                           └────────┬───────────────────────────┘
                                    ▼
                      ~/.workbuddy/settings.json
                      （botToken / userId / baseUrl）
```

**关键认知：收和发是两条独立的路。**

- **收消息**：WorkBuddy 桌面端常驻一个轮询进程，不停调 `/ilink/bot/getupdates`。只要 WorkBuddy 开着，你在微信说什么它都收得到。这条路几乎不会坏。
- **发消息**：调 `/ilink/bot/sendmessage`。这是完全独立的一次 HTTP 请求，**不依赖 WorkBuddy 进程**，只要有 token 谁都能调。但它受微信服务端的"主动推送会话"策略限制。

很多人排查时的误区就是：「我微信明明能收到 bot 回复，怎么推送就是不行？」——因为那是两回事。

## 3. 为什么不直接用 WorkBuddy 自带的「推送到微信」

WorkBuddy 的自动化任务（automations 表）确实有个 `push_to_wechat` 字段，开启后理论上会把任务结果自动投递到微信。它的实现是：

```
任务执行完 → 写入 automation_delivery_outbox 表 → 后台投递器读取 → 调 sendmessage
```

实测下来的问题：

1. **投递失败不告警**。失败记录静静躺在 `automation_delivery_outbox` 表的 `last_error_message` 字段里，界面上看不到。
2. **重试策略不透明**。`max_attempts` 用完就永久丢弃。
3. **无法自定义内容格式**。它推送的是任务的原始输出，可能很长、带 markdown、手机上不好读。
4. **和任务提示词耦合**。你没法在任务里判断"推送成功了没"然后做补救。

自定义脚本方案的优势：

| | 原生 push_to_wechat | 自定义脚本 |
|---|---|---|
| 失败可见 | ❌ 只能查数据库 | ✅ 命令行直接返回错误码 |
| 内容可控 | ❌ 原样投递 | ✅ 任意裁剪、加前缀、限长 |
| 跨 Agent | ❌ 仅 WorkBuddy 自动化 | ✅ Codex / Claude Code / cron / 任何脚本 |
| 可调试 | ❌ | ✅ 随时手动跑一次验证 |

## 4. 消息协议的三层结构

一条 `sendmessage` 请求，从外到内是三层：

### 第一层：HTTP 请求头（身份认证 + 客户端指纹）

微信服务端会校验调用方是不是合法客户端。缺任何一个头都会被拒。

```
Authorization: Bearer d2cc68bff868@im.bot:0600002...
AuthorizationType: ilink_bot_token
X-WECHAT-UIN: <随机数的 base64>
iLink-App-Id: bot
iLink-App-ClientVersion: 132102
Content-Type: application/json
```

⚠️ **最容易踩的坑**：`Authorization` 里的 token **必须包含 `accountId:` 前缀**。也就是完整形式 `d2cc68bff868@im.bot:0600002xxx`，而不是只有冒号后面那串。少了前缀直接返回 `errcode=-14 session timeout`——这个错误信息极具误导性，会让你以为是会话过期，实际是格式错误。

### 第二层：`base_info`（协议版本协商）

```json
"base_info": {
  "channel_version": "2.4.6",
  "bot_agent": "OpenClaw"
}
```

版本号必须和官方 SDK 对齐。用旧版本号（比如自己编的 `my-app-1.0.0`）会被服务端拒绝。

### 第三层：`msg`（消息本体）

```json
"msg": {
  "from_user_id": "",
  "to_user_id": "o9cq80-...@im.wechat",
  "client_id": "a3f9c2e1b8d74506",
  "message_type": 2,
  "message_state": 2,
  "item_list": [{"type": 1, "text_item": {"text": "内容"}}],
  "context_token": ""
}
```

## 5. `context_token` —— 整套机制的核心

这是最需要理解的一个字段。

**它是什么**：一次会话上下文的凭据。可以理解为"我这条消息是接着哪次对话说的"。

**为什么需要它**：微信不允许 bot 无限期、无条件地主动骚扰用户。必须有一个"用户最近跟我说过话"的证据，才允许推送。

**两种用法**：

| 场景 | context_token | 说明 |
|---|---|---|
| 纯文本消息 | 可传空串 `""` | 服务端自动用你和 bot 之间**最近一次会话**兜底 |
| 图片/文件/视频 | 必须传真实值 | 从 `~/.workbuddy/claw-state/weixin/<accountId>_im.bot.cursor.json` 的 `get_updates_buf` 字段读取 |

**空串兜底的代价**：那个"最近一次会话"是有时效的。实测时间线：

```
22:18  用户在微信主动给 bot 发了一条消息  ← 会话建立
22:36  推送成功
23:31  推送成功
00:27  推送成功
01:22  推送失败 ret=-2: prepare failed  ← 会话失效
...    持续失败 7 次
08:25  用户再次在微信主动发消息          ← 会话重建
08:26  推送成功
```

所以有效窗口大约是**数小时**（本次约 3 小时余），且具体时长由微信服务端策略决定，**客户端无法延长、无法续期**。

这就是为什么无人值守的定时推送不能保证 100% 送达。应对方案见 `07-故障排查.md` 和 `08-已知限制.md`。

## 6. `client_id` 的作用

```python
"client_id": uuid.uuid4().hex[:16]
```

16 位随机 hex，服务端拿它做**幂等去重**。同一个 client_id 重复提交只会发一条。

实践建议：每次发送都生成新的随机值。如果你要实现"失败重试"，重试时应该**复用同一个 client_id**，避免网络抖动导致用户收到两条一样的消息。

---

## 7. 消息类型枚举

| 字段 | 值 | 含义 |
|---|---|---|
| `message_type` | 2 | 主动下发消息 |
| `message_state` | 2 | 消息已完成（非流式中间态） |
| `item_list[].type` | 1 | 纯文本 |
| `item_list[].type` | 其他 | 图片/文件/卡片等，需配合 `getuploadurl` |

流式场景（比如 AI 边生成边显示）会用 `message_state` 的其他值，本方案不涉及。

## 8. 可用端点清单

从 WorkBuddy 客户端逆向出的全部 iLink Bot 端点：

| 端点 | 方法 | 用途 |
|---|---|---|
| `/ilink/bot/sendmessage` | POST | 发送消息 ⭐ |
| `/ilink/bot/getupdates` | POST | 拉取消息（长轮询） |
| `/ilink/bot/getuploadurl` | POST | 获取文件上传地址 |
| `/ilink/bot/get_bot_qrcode` | GET | 获取绑定二维码（`bot_type=3`） |
| `/ilink/bot/get_qrcode_status` | GET | 轮询扫码状态 |

**注意**：没有 `set_profile` / `update_bot_info` 这类端点。所以 bot 的**头像和昵称改不了**，那是平台侧注册时定死的。你只能在微信里给它设备注名（仅本地显示）。
